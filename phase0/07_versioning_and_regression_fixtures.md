# Phase 0 — Versioning Strategy and Regression Fixtures

Program: [EO_PREDICTIVE_ARCHITECTURE_PROGRAM.md](../EO_PREDICTIVE_ARCHITECTURE_PROGRAM.md)
Status: charter (Phase 0). Policy. No implementation.
Version: `phase0.1.0`
Date: 2026-07-07

## Purpose

Specify how policy versions are named, incremented, and preserved; and enumerate the regression fixture charts every new method must be tested against.

## 1. Versioning strategy

### 1.1 Version scheme

Format: `<epoch>.<major>.<minor>`.

- `<epoch>` — phase-scale marker. Phase 0 uses `phase0`. When the program crosses into a materially new architectural regime, epoch bumps. Not a semver `major`.
- `<major>` — incompatible policy change within an epoch. Requires operator sign-off. Old sidecars remain valid records against the old major.
- `<minor>` — backward-compatible policy change (added optional field, expanded enum, clarified rationale). Does not require sign-off for the change itself, but does require an update to `agents/REVISIONS.md`.

Example progression during Phase 0 sign-off cycle: `phase0.1.0` → `phase0.1.1` (clarification) → `phase0.2.0` (asteroid tier rebalance) → `phase1.0.0` (Phase 1 sidecar writer landed).

### 1.2 Separate version tracks

Each of the following has its own version string. They do not have to move in lockstep.

- `predictive_object_schemas` (from [01_predictive_object_schemas.md](./01_predictive_object_schemas.md))
- `asteroid_registry` (from [02_asteroid_predictive_registry.json](./02_asteroid_predictive_registry.json))
- `method_charters` (from [03_method_charters.md](./03_method_charters.md); may be split per-clock in a later revision)
- `convergence_protocol` (from [04_convergence_and_candidate_protocol.md](./04_convergence_and_candidate_protocol.md))
- `candidate_protocol` (from [04](./04_convergence_and_candidate_protocol.md) §4)
- `validation_protocol` (from [05_validation_protocol.md](./05_validation_protocol.md))
- `sidecar_contract` (from [06_sidecar_and_export_contract.md](./06_sidecar_and_export_contract.md))
- `component_score_weights` (from [04](./04_convergence_and_candidate_protocol.md) §5.2)
- `detector_thresholds` (from [06](./06_sidecar_and_export_contract.md) §2.14; snapshotted values)

Every version string appears in every sidecar under `policy_versions`.

### 1.3 Version promotion rules

A version bump requires:

- The changed file's header updated.
- The version reference in every other Phase 0 file that cites it updated.
- An `agents/REVISIONS.md` entry describing the change.
- If `major` or `epoch`: an operator sign-off note.

Version bumps must not silently change the meaning of an old version. If a definition changes, it takes a new version; the old version's meaning is preserved.

### 1.4 Historical preservation

- Every previously-shipped policy version's *source-of-truth files* are preserved in the repository at their sign-off state. Consider Git tags per version (`phase0/v1.0.0`, `phase0/v1.1.0`, etc.) as the concrete mechanism.
- Old sidecars remain reproducible: a sidecar carrying `policy_versions.asteroid_registry = phase0.1.0` can be re-generated by checking out the tag.
- No auto-migration of old sidecars to new schemas. Old sidecars are historical records, not living objects.

### 1.5 Governance registry vs. asteroid predictive registry

- `formulas/governance_registry.py` remains authoritative for **body eligibility per report type** (natal-layer visibility policy).
- `phase0/02_asteroid_predictive_registry.json` is authoritative for **asteroid predictive behavior** (forecast-layer policy).
- Where they overlap (both mention asteroid eligibility), the governance registry is authoritative for consumer-report surfacing; the asteroid predictive registry is authoritative for predictive-engine participation.
- Bumping one does not require bumping the other.

## 2. Regression fixture chart specifications

The program requires ≥8 fixture chart types. Every new clock, every registry change, and every candidate-protocol change re-runs against these fixtures.

Fixtures live in `tests/fixtures/phase0/` (path to be established at Phase 1). Each fixture is a JSON file with birth data, expected sidecar bit-exact hash (post-detector-threshold snapshot), and per-clock expected counts.

### 2.1 Fixture #1 — `exact_birth_time_ordinary_year`

Purpose: baseline. Exact birth time, no unusual features. Report over a calendar year with average transit density.

Specs:

- Birth: `1985-04-15` at `13:22:00` in a temperate northern-hemisphere location.
- Report window: `2026-01-01` to `2027-01-01`.
- Expected: normal count of transit cycles, 3–5 predictive windows, ~13 lunar returns, 1 solar return.
- Anchor confidence: `hard`-eligible.
- Asteroid activity: moderate. Kassandra transit contact expected mid-year (specific date documented at fixture write time).

### 2.2 Fixture #2 — `uncertain_birth_time`

Purpose: birth-time-confidence gating. `simple_mode` chart (noon fallback) or approximate birth time (documented DST gap).

Specs:

- Birth: `1972-06-21` with `simple_mode = True`.
- Report window: same as Fixture #1.
- Expected: all angle-involving candidates carry `birth_time_dependency = hard` and `confidence_state = withheld`. Solar returns emit but return-chart interpretation withholds angle claims.
- Sidecar validation: no candidate has `candidate_status = pre_registered` if its `birth_time_dependency = hard`.

### 2.3 Fixture #3 — `asteroid_heavy_chart`

Purpose: exercise the full asteroid registry. Chart with multiple anchor-tier asteroids in tight aspect to angles and luminaries.

Specs:

- Chart selected so that ≥4 anchor-tier asteroids (Kassandra, Destinn, Karma, Aletheia, Kaali, Medea, Hermes, Chaos) fall within 3° of ASC/MC/Sun/Moon.
- Report window: 1 year.
- Expected: multiple asteroid-participating candidates, high `asteroid_specificity` scores, `asteroid_diagnostics.asteroids_active_as_target` includes ≥4 anchor asteroids.
- Sidecar validation: every asteroid contact traces from natal position → registry policy → produced event → normalized signal → sidecar provenance.

### 2.4 Fixture #4 — `quiet_transit_year`

Purpose: quiet-period behavior. Chart + report window with unusually few structural transits.

Specs:

- Chart selected such that no outer-planet transit makes a major aspect to any natal luminary or angle during the report window.
- Expected: zero or very few `MicroCandidate` emissions. `debug.quiet_period = true` when candidate count is zero.
- Validation: matched-random baseline should behave symmetrically (few matches).

### 2.5 Fixture #5 — `dense_transit_year`

Purpose: dense-period behavior. Chart + report window with multiple structural transits overlapping.

Specs:

- Chart selected such that ≥3 outer-planet transits are within orb of luminaries or angles for at least half the report window.
- Expected: high candidate count, high complexity scores, coherence graph shows multiple strands.
- Anti-stacking validation: composite dedup keeps `independent_method_families` counts sane.

### 2.6 Fixture #6 — `known_retrograde_loop`

Purpose: multi-pass cycle behavior. Chart + window with a known outer-planet retrograde loop targeting a natal body.

Specs:

- Loop selected such that a slow planet (Saturn/Jupiter) makes three exact contacts to a natal luminary via retrograde loop within the report window.
- Expected: `cycle_id` shared across all three passes; `contact_count = 3`; `multiple_exact_passes = true`; anti-stacking treats the cycle as one vote.

### 2.7 Fixture #7 — `eclipse_heavy_period`

Purpose: eclipse dedup and lunation-family behavior. Report window with ≥3 eclipses.

Specs:

- Report window selected containing a known eclipse-dense period (e.g. spanning a nodal cycle max).
- Expected: eclipses correctly suppress same-date plain lunations; `independence_group = "lunation_family"` counts eclipses as one family; per-eclipse natal-contact matches trace correctly.

### 2.8 Fixture #8 — `multiple_simultaneous_long_clocks`

Purpose: multi-clock convergence. Chart + window with active ZR peak + profection year + return + Solar Arc contact + progression contact all overlapping.

Specs:

- Chart + window selected so that (once ZR and Solar Arc are implemented in Phase 5/6) at least three long clocks are simultaneously active on a shared natal anchor.
- Expected: `MicroCandidate` with `|independent_method_families| ≥ 3` (before dedup); high `long_clock_support`; multi-strand coherence graph collapses to single connected component.

### 2.9 Fixture #9 (recommended) — `angle_boundary_case`

Purpose: birth-time-gating edge case. Birth time at a moment when the natal Ascendant is within 0.5° of a sign boundary.

Specs:

- Birth time deliberately positioned so a small time shift would move Ascendant into the next sign.
- Expected: `low` confidence flag on angle-derived claims; whole-sign profection is still computable (uses Ascendant sign, not degree); ZR from Fortune (which uses Ascendant degree) carries `confidence_state = low`.

### 2.10 Fixture #10 (recommended) — `high_latitude_polar_chart`

Purpose: extreme-latitude behavior. Confirm the Porphyry-fallback branch in `natal_engine.py` correctly triggers.

Specs:

- Birth at latitude > 66.5° (inside polar circle).
- Expected: chart computes without error using Porphyry fallback; whole-sign houses still assigned; angle-dependent claims may be reduced-confidence.

## 3. Fixture governance

- Fixtures are versioned along with policy: `tests/fixtures/phase0/fixture_01_exact_birth_time_ordinary_year.v1.0.0.json`.
- A fixture change (birth data, report window, expected counts) is a version bump.
- Fixture expected outputs are recorded as bit-exact sidecar hashes computed at initial fixture setup. A test failure = a diff between current sidecar and the expected hash. The diff must be explicable and approved before the fixture is updated.

## 4. Fixture usage per phase

- **Phase 1** (sidecar writer): all fixtures generate sidecars successfully. Bit-exact hashes recorded as baseline.
- **Phase 2** (asteroid activation): fixture #3 must show asteroid participation traces; fixture #1 must remain byte-identical for non-asteroid content.
- **Phase 3** (shared clock framework): fixtures re-run and any diff to prior baseline must be an intentional method-charter update.
- **Phase 4** (returns + profections): fixture #1 must show 1 solar return, 13 lunar returns; every fixture gets its profection year.
- **Phase 5** (Solar Arc + progressions): fixture #6 must include progression events; fixture #8 gains multi-clock convergence.
- **Phase 6** (Lots + ZR): fixture #8 becomes the primary multi-clock demonstration.
- **Phase 7** (cross-clock convergence): candidates emitted for fixtures where expected.
- **Phase 8** (discrete candidate engine): fixture-level candidate counts recorded as regression baselines, including the observed distribution of trigger-derived `window_days` per fixture (no fixed target width expected — see [04_convergence_and_candidate_protocol.md](./04_convergence_and_candidate_protocol.md) §4.2).
- **Phase 9** (validation): matched-random baselines run against fixtures for calibration checks.

## 5. Non-fixture regression tests

Existing `tests/` directory tests continue. Nothing in Phase 0 removes or replaces them.

The fixture suite is *additional* — a per-phase gate ensuring policy versions are traceable.

## 6. Locked at Phase 0

- Three-level version scheme (§1.1).
- Separate version tracks per policy artifact (§1.2).
- Historical preservation via Git tagging (§1.4).
- Minimum 8 fixture chart types (§2.1–§2.8), 10 recommended (§2.9–§2.10).
- Bit-exact sidecar hashes as fixture expected outputs (§3).

Any change requires a policy-version bump.
